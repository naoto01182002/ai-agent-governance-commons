# AI Agent Governance Commons 標準化方針

## 1. 位置づけ

本ドキュメントは、AI Agent Governance Commons における標準化の考え方を定義する。

AI Agent Governance Commons は、AIエージェントを中央集権化させず、企業システム・SI・RFP・API・運用設計・監査設計に注入可能な公共標準を整備するための構想である。

本標準化方針は、特定AIモデル、特定クラウド、特定ベンダー、特定OSSのための仕様ではない。
企業、SIer、情シス、監査、法務、業務部門、アーキテクトが、AIエージェント導入時に同じ観点で設計・評価・監査できるようにするための共通言語である。

---

## 2. 標準化の目的

AIエージェントは今後、人間や企業の代理として、調査、提案、設計、開発、運用、監査、承認補助、業務実行支援を担うようになる。

しかし、AIエージェントが業務システム、API、外部ツール、他社エージェントに接続するようになると、以下の問題が発生する。

* AIは誰の代理で動いているのか
* AIにはどこまで権限があるのか
* AIは何を参照して判断したのか
* AIは何を提案し、何を実行したのか
* 高リスク操作に人間承認は入っているのか
* 人間はAIを停止できるのか
* 事故時に誰が責任を負うのか
* 他エージェントと連携した場合、責任境界はどこにあるのか
* 監査・法務・情シスが後から説明できる証跡は残るのか

本標準化の目的は、これらの問いに対して、企業システムに注入可能な形で最低限の共通仕様を定義することである。

---

## 3. 標準化の基本姿勢

AI Agent Governance Commons の標準化では、以下を重視する。

* 実務に注入できること
* RFPに記載できること
* 要件定義に落とせること
* 設計書に転記できること
* API仕様に反映できること
* 監査ログとして検証できること
* RACIとして責任分界を示せること
* 特定ベンダーに依存しないこと
* 導入コストが過大になりすぎないこと
* 人間の承認負荷を増やしすぎないこと
* 事故時に責任が霧散しないこと
* AIを止めるのではなく、安全に使う前提を整えること

標準は、理想論として美しいだけでは不十分である。
企業、SIer、情シス、監査、法務が実際に使える粒度でなければならない。

---

## 4. 標準化の中核思想

AI Agent Governance Commons の標準化は、以下の思想に基づく。

> モデルは借りてもよい。
> しかし、業務文脈・権限・監査ログ・停止権・責任分界は社会側に残す。

AIモデルやクラウドサービスは外部から利用してよい。
しかし、AIにどこまで業務代理権を与えるのか、どの操作を許可するのか、どの証跡を残すのか、誰が最終責任を負うのかは、利用者側・企業側・業界側・社会側で定義すべきである。

標準化の目的は、AI活用を止めることではない。
AIエージェントが企業活動に安全に入れるための統治構造を先に定義することである。

---

## 5. 標準化レイヤー

AI Agent Governance Commons の標準は、以下の4層で整理する。

---

### 5.1 Philosophy Layer

AIを中央集権化させないための思想層である。

主な対象は以下。

* 反中央集権
* 公共標準
* 文脈主権
* 人間主権
* 既存アーキテクチャへの注入
* AIに権力を集中させない設計思想

この層では、AIエージェント社会をどのような価値観で設計するかを定義する。

---

### 5.2 Governance Layer

AIエージェントを統治するための制御層である。

主な対象は以下。

* AIエージェント権限管理
* AIリスク分類
* AI監査ログ
* Human-on-the-loop
* Human Sovereignty Gate
* AI停止権
* AI Agent RACI
* A2A責任分界

この層では、AIが勝手に動くのではなく、権限・監査・承認・停止・責任分界の中で動作するための標準を定義する。

---

### 5.3 Enterprise Adoption Layer

企業システムへ導入するための実務層である。

主な対象は以下。

* RFP
* 要件定義
* 機能設計書
* API設計書
* 運用設計書
* 監査設計
* 変更管理
* Self-Assessment
* SIer提案テンプレート

この層では、標準を企業の実務文書へ注入する方法を定義する。

---

### 5.4 Economic Enforcement Layer

企業が採用する理由を作るための経済的強制力の層である。

主な対象は以下。

* 監査
* 保険
* 契約
* 稟議
* リスク評価
* ベンダー評価
* SI提案価値
* 内部統制
* 委託先管理

企業は「正しいから」だけでは動かない。
監査に通る、保険に入りやすい、RFPで評価される、事故時に説明しやすい、契約上の責任分界が明確になる、といった実務上の利益が必要である。

---

## 6. Minimum Viable Standard

初期段階で最低限定義すべき標準を **Minimum Viable Standard v1.0 Public Draft** とする。

### 6.1 必須10項目

1. AIは誰の代理かを明示する
2. AIの権限を明示する
3. AIが参照した情報を記録する
4. AIが提案した内容を記録する
5. AIが実行した操作を記録する
6. 高リスク操作は人間承認を必須にする
7. 人間がAIを停止できる
8. ロールバックまたは取消手段を定義する
9. 責任主体をRACIで明確化する
10. 他エージェントと連携する場合、利用範囲と責任境界を明示する

この10項目を、AI Agent Governance Commons の初期の最低説明項目とする。

これは安全認証、外部準拠審査、適合保証を意味しない。MVS v1.0 Public Draft は、「この項目を説明できないAIエージェント導入は、企業統制、委託先管理、監査、法務レビューに接続できていない」という最低限の説明要求として扱う。

---

## 7. AIエージェント権限標準

AIエージェントの権限は、少なくとも以下に分類する。

| 権限                    | 内容                |
| --------------------- | ----------------- |
| read                  | 情報を参照する           |
| analyze               | 情報を分析する           |
| suggest               | 提案を作成する           |
| draft                 | 文書・申請・回答の下書きを作成する |
| request_approval      | 人間に承認を依頼する        |
| execute_low_risk      | 定義済みの低リスク操作を実行する  |
| execute_with_approval | 人間承認後に実行する        |
| prohibited            | 実行禁止              |

標準化では、AIができることだけでなく、AIがしてはならないことを明確にする。

特に以下は原則として禁止または高リスク操作とする。

* 本番DBの直接更新
* 契約締結
* 送金
* 与信確定
* 発注確定
* 価格確定
* 個人情報の外部送信
* 権限体系の変更
* 監査ログの削除・改変
* 人間停止権の無効化

---

## 8. AIリスク分類標準

AIエージェントの行為は、リスクに応じて分類する。

| リスク区分 | 内容                        | 人間関与        |
| ----- | ------------------------- | ----------- |
| 低リスク  | 文書要約、分類、候補作成、ログ整理など       | 事後ログのみ      |
| 中リスク  | 判断補助、申請下書き、対応案作成など        | 事後監査または例外確認 |
| 高リスク  | 金銭・契約・外部影響・業務確定に関わる操作     | 事前承認必須      |
| 最高リスク | 権限体系、監査ルール、停止権、ガバナンス構造の変更 | 人間評議会承認必須   |
| 禁止行為  | 人間主権や監査可能性を破壊する操作         | 実行不可        |

標準化では、すべてを人間承認にしない。
人間の注意力を有限資源として扱い、高リスク判断に集中させる。

---

## 9. Human-on-the-loop 標準

Human-on-the-loop は、AIの全処理を人間が逐一承認する仕組みではない。

AIが低リスク・中リスク業務を一定範囲で自律処理し、人間はリスクの高い判断、例外、不可逆操作、対外影響のある判断に集中する仕組みである。

### 9.1 基本方針

* 低リスクはAIが処理し、ログを残す
* 中リスクはAIが処理し、人間は事後監査する
* 高リスクは人間が事前承認する
* 最高リスクは人間評議会または責任者会議が承認する
* 例外、異常、閾値超過は人間にエスカレーションする

### 9.2 承認疲労への対応

Human-on-the-loop では、承認疲労を防ぐために以下を設計する。

* 承認対象をリスクベースで絞る
* 類似案件はバッチ承認ではなくパターン承認にする
* 事後監査やサンプリングを併用する
* 承認件数、却下件数、差し戻し件数を監査する
* 承認が形骸化していないか定期レビューする

---

## 10. Human Sovereignty Gate 標準

Human Sovereignty Gate は、人間の最終停止権を定義する標準である。

中核メッセージは以下である。

> いつでも止められるから、任せられる。

AIが論理的に正しく見える判断を行ったとしても、統治される側である人間が受け入れない統治構造変更は正統性を持たない。

### 10.1 対象

Human Sovereignty Gate は、以下に適用する。

* ガバナンス構造の変更
* 権限体系の変更
* 監査ルールの変更
* 停止権の変更
* 高リスク操作の自動化範囲拡大
* AIによる不可逆操作の追加
* 対外的な法的・金銭的影響を持つ操作の自動化

### 10.2 人間停止権の扱い

* 人間の停止権はAIが無効化できない
* 停止理由は記録する
* 停止は永久否決ではなく、期限付き凍結として扱える
* 一定期間後に再提案可能とする
* 停止判断の傾向は監査対象にする
* ただし、AIが人間停止権を無効化する経路は持たない

### 10.3 設計書に置く項目

Human Sovereignty Gate を設計書に記述する場合、少なくとも以下を置く。

* gate_target
* trigger_condition
* approver_role
* stop_authority_role
* decision_type
* reason_code
* freeze_until
* resubmission_requirements
* exception_approval_allowed
* proxy_approval_allowed
* conflict_of_interest_check
* fatigue_review_interval
* audit_log_ref

---

## 11. AI監査ログ標準

AIエージェントの行動は、事後に検証可能でなければならない。

監査ログは、AIの内部思考をすべて保存するものではない。
誰の代理で、何を参照し、何を判断し、何を提案し、何を実行したかを復元するための証跡である。

### 11.1 必須項目

* agent_id
* owner_id
* acting_on_behalf_of
* authority_scope
* input_refs
* context_refs
* tool_calls
* decision_summary
* risk_classification
* human_approval_status
* output_refs
* audit_log_id
* rollback_policy
* timestamp

### 11.2 監査ログの目的

* 事故時に判断経緯を説明する
* 権限逸脱を検出する
* 人間承認の有無を確認する
* 責任分界を復元する
* ベンダー・SIer・業務部門間の説明材料にする
* 保険・監査・法務レビューの証跡にする

---

## 12. AI Agent RACI 標準

AIエージェントが関与する業務では、RACIを定義する。

| 区分          | 内容                  |
| ----------- | ------------------- |
| Responsible | 実行責任。操作・提案・処理を担った主体 |
| Accountable | 最終責任。業務オーナー、法人、責任者  |
| Consulted   | 判断時に参照された専門家・専門AI   |
| Informed    | 結果通知を受ける関係者         |

AIはResponsibleまたはConsultedにはなり得る。
しかし、AIはAccountableにはならない。

最終責任は、人間、業務部門、法人、または契約上の責任主体に置く。

---

## 13. A2A責任分界標準

AI同士、企業間、ベンダー間でエージェントが連携する場合、応答には利用範囲と責任境界を付与する。

### 13.1 必須項目

* provider_agent_id
* provider_owner
* consumer_agent_id
* consumer_owner
* response_type
* confidence
* data_source
* data_timestamp
* valid_until
* usage_scope
* not_authorized_for
* liability_boundary
* consumer_responsibility
* contract_ref
* incident_contact
* audit_log_id

AI同士のやり取りを単なる自然言語応答にせず、契約、委託先管理、監査ログ、障害時連絡に接続できる証跡付きメッセージとして扱う。

提供側は、提供した情報の範囲、鮮度、利用禁止用途を明示する。利用側は、他社エージェントの出力をそのまま業務確定に使わず、自社側の再判断責任を負う。

### 13.2 目的

A2A責任分界は、以下を防ぐために必要である。

* 他社AIの出力を誤用する
* データ提供側と利用側が責任を押し付け合う
* AI同士の判断経緯が追跡できなくなる
* 事故時に責任主体が霧散する
* 契約・監査・保険で説明できなくなる

## 14. API Agent Context 標準

AIエージェントがAPIを呼び出す場合、APIリクエストには agent_context を付与する。

### 14.1 agent_context の目的

agent_context は、AIが誰の代理で、どの権限で、どの目的でAPIを呼び出したかを追跡可能にするための情報である。

### 14.2 必須項目例

```json
{
  "agent_id": "agent-001",
  "owner_id": "company-a",
  "acting_on_behalf_of": "operations-team",
  "authority_scope": ["read", "analyze", "draft"],
  "human_approved": false,
  "risk_classification": "medium",
  "audit_log_id": "audit-20260506-001",
  "rollback_policy": "manual_approval_required"
}
```

## 15. RFP・設計書への注入標準

標準は、RFPや設計書に転記できなければ普及しない。

したがって、AI Agent Governance Commons では、以下への注入を前提とする。

### 15.1 RFP

RFPには以下を評価項目として入れる。

* AIエージェントの権限設計があるか
* AIがDBを直接更新しないか
* AIが業務実行APIを通すか
* AI監査ログが残るか
* Human-on-the-loop が設計されているか
* Human Sovereignty Gate が定義されているか
* RACIが定義されているか
* A2A責任分界があるか
* モデル・クラウドロックインを回避できるか

RFP追補は、質問リストだけでなく、評価観点、最低失格条件、提出証跡、設計書・監査ログ・RACIとの対応欄、配点例を含む実務テンプレートとして扱う。

ただし、配点そのものは標準化しない。Commons は評価カテゴリと最低失格条件を標準化し、点数配分は発注者が案件リスクに応じて調整する。

最低失格条件の初期案は以下とする。

* AIが本番DBを直接更新する設計で、承認、監査、取消手段がない
* AIに監査ログの削除または改変を許す
* AIが人間停止権を無効化できる
* AIをRACIのAccountableに置く
* 高リスク操作に人間承認がない
* A2A連携で利用範囲と責任境界を示さない

### 15.2 設計書

機能設計書、API設計書、運用設計書には以下の欄を追加する。

* AI利用有無
* AIの役割
* AIが参照するデータ
* AIが提案する内容
* AIが実行可能な操作
* 人間承認要否
* 監査ログ要否
* 停止条件
* ロールバック条件
* RACI

## 16. Self-Assessment 標準

初期段階では、公的認証を狙わない。
まずは企業やSIerが自らチェックできる Self-Assessment Checklist を整備する。

### 16.1 チェック観点

* AIは誰の代理か明示されているか
* AIの権限は明示されているか
* AI監査ログは残るか
* 高リスク操作に人間承認はあるか
* 人間がAIを停止できるか
* RACIは定義されているか
* A2A連携時の責任境界は明示されているか
* ロールバックまたは取消手段はあるか
* モデル・クラウドロックインを避けられるか
* 監査・法務・情シスがレビュー可能か

## 17. 標準化の進め方

標準化は以下の順序で進める。

1. 方針の明文化
2. Minimum Viable Standard の確定
3. 権限モデルの整理
4. リスク分類の整理
5. 監査ログ標準の整理
6. Human-on-the-loop の整理
7. Human Sovereignty Gate の整理
8. RACI の整理
9. A2A責任分界の整理
10. RFP追補テンプレートの作成
11. Self-Assessment Checklist の作成
12. 批判と再考による更新

---

## 18. 批判を標準化プロセスに組み込む

標準は、正しさだけでは普及しない。

以下の批判を常に確認する。

* 誰がコストを負担するのか
* 企業が採用する理由はあるか
* 人間承認が形骸化しないか
* 責任分界が曖昧ではないか
* マルチベンダー間で責任の押し付け合いにならないか
* Commons自体を誰が維持するのか
* ビッグテックが類似標準を出したときに差別化できるか
* 標準が重すぎて導入されないのではないか
* 標準が軽すぎて実効性を持たないのではないか

批判は標準化の敵ではない。
標準を現実に耐える形へ鍛えるための必須プロセスである。

---

## 19. 普及方針

最初から公的認証を狙わない。

まずは、以下のような実務テンプレートとして使われることを目指す。

* RFP追補テンプレート
* 権限マトリクス
* 監査ログサンプル
* RACIテンプレート
* A2A責任分界テンプレート
* Self-Assessment Checklist

標準化は宣言ではなく、既成事実によって進む。

初期の普及経路は以下を想定する。

1. RFP追補テンプレートとして使われる
2. SIerの提案・設計標準に組み込まれる
3. 企業の社内標準・チェックリストに入る
4. 内部監査・法務・情シスが参照する
5. 監査法人・保険会社が後追いで参照する
6. 業界標準化の議論に接続する

---

## 20. 最終メッセージ

AI Agent Governance Commons の標準化は、AI活用を止めるためのものではない。

AIを安全に、説明可能に、責任追跡可能に、そして中央集権化させずに企業システムへ組み込むためのものである。

AIエージェント社会の勝負は、誰が最も強いAIを持つかではない。

重要なのは、誰がAIに権限を与え、誰が監査し、誰が止められ、事故時に誰が責任を負うかを、公共的な標準として先に定義できるかである。

> AIを使う社会ではなく、AIに権力を集中させない社会を設計する。
